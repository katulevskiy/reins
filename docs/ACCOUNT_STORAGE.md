# Mobile account storage

An account is identified by its authenticated server URL and stable server user ID. Every login creates a separate engine, SQLite connection, integration registry and connector sessions. Requests capture that engine and an account generation before they enter the core runtime. Logout cancels account work, closes the connection, drops its data key, and invalidates its session. Native screens and refreshes also use account generations.

SQLite runs in memory. The complete database is serialized and encrypted with AES-256-GCM before an atomic, durable disk write. This includes activity labels and details, grants, accounts, integration names, MCP configuration, credentials, pinned computer keys and Autopilot state. No plaintext SQLite database, journal or temporary database is used for an account. Its data key is HMAC-SHA256 of the account vault key with a domain-separated server/user identity. Ciphertext also authenticates that identity. Wrong keys, changed owners and copied files fail closed.

The installation control store is encrypted in full under a device key wrapped by Android Keystore or the iOS device-only keychain. It retains the authenticated session and sealed, identity-scoped account key caches. Account session refresh and logout check the active owner within the control-store lock. Selecting a different account and saving its session is atomic. A cached account key is selected only after an authenticated identity matches its server and user ID.

Portable account snapshots omit installation keys, refresh tokens, outstanding prompts and temporary sign-in state. The client encrypts snapshots before uploading them to `/reins/api/account-state`. Authenticated users read only their own ciphertext. Updates require the account's registered approval device, an expected revision, and a successful compare-and-swap. The encryption authenticates the revision as well as the owner. Another phone opens the state only after it obtains the same account's vault key through its password, recovery code or approved key transfer. Conflicting changes preserve the local encrypted copy and fail rather than overwrite permissions.

Android native reminder and browser sign-in caches are encrypted under separate Keystore keys. iOS widget snapshots are encrypted under a device-only shared keychain key. Account changes discard screen models and decrypted views; logout removes account notifications and reminders.

On upgrade, legacy SQLite is encrypted durably before its plaintext files are removed. The old database had no trustworthy ownership boundary for its history, grants or integration credentials, so those mixed records remain in encrypted quarantine and are never assigned to whichever account signs in next. Previously stored recovery secrets can be recovered only through their verified server/user binding and successful decryption of that account's vault key. Integrations from the mixed legacy store need to be connected again under their owner.
