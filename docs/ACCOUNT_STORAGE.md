# Mobile account storage

An account is identified by its authenticated server URL and stable server user ID. Every login creates a separate engine, SQLite connection, integration registry and connector sessions. Requests capture that engine and an account generation before they enter the core runtime. Logout cancels account work, closes the connection, drops its data key, and invalidates its session. Native screens and refreshes also use account generations.

SQLite runs in memory. The complete database is serialized and encrypted with AES-256-GCM before an atomic, durable disk write. This includes activity labels and details, grants, accounts, integration names, MCP configuration, credentials, pinned computer keys and Autopilot state. No plaintext SQLite database, journal or temporary database is used for an account. Its data key is HMAC-SHA256 of the account vault key with a domain-separated server/user identity. Ciphertext also authenticates that identity. Wrong keys, changed owners and copied files fail closed.

The installation control store is encrypted in full under a device key wrapped by Android Keystore or the iOS device-only keychain. It retains the authenticated session and sealed, identity-scoped account key caches. Account session refresh and logout check the active owner within the control-store lock. Selecting a different account and saving its session is atomic. A cached account key is selected only after an authenticated identity matches its server and user ID.

Portable account snapshots omit installation keys, refresh tokens, outstanding prompts and temporary sign-in state. The client encrypts snapshots before uploading them to `/reins/api/account-state`. Authenticated users read only their own ciphertext. Updates require the account's registered approval device, an expected revision, and a successful compare-and-swap. The encryption authenticates the revision as well as the owner. Another phone opens the state only after it obtains the same account's vault key through its password, recovery code or approved key transfer.

Phones never lock each other out. Each keeps the last state it agreed on with the server (the merge base) in a separate file sealed with the installation's device key, its authenticated data naming the account and the revision. An upload that loses the compare-and-swap, and a phone that opens with changes the server never got (it was not the approval device, or the app ended first), pull the server's state and merge it record by record. The merge is uploaded with the same compare-and-swap and retried on a race.

What is synced and how each table merges:

| table | merge |
|---|---|
| `grants` | Never more permissive than either phone or the base, whatever the clocks: revoked in any version stays revoked; a scope, account or connection that differs is revoked; the earliest expiry, the smallest use limit, every use counted. A grant deleted on either phone stays deleted: deletions leave tombstones (`meta`, kept for good), so a merge without a base cannot bring one back. |
| `autopilot_settings` | Changed on one side only: that side's, so a lockdown cleared or a bypass stopped on one phone stays so. Changed on both: lockdown wins; otherwise the less permissive mode, and a bypass ends at the earlier time, so one stopped on either side stays stopped. Clocks decide nothing. |
| `audit` (Activity) | A grow-only union of both phones' entries, trimmed to the retention. Never a conflict. |
| `autopilot_memory` | Entries added on either side are kept; one forgotten on either side is gone. |
| `meta` | Per key. JSON settings merge entry by entry, and "ask every time" wins. |
| `accounts`, `secrets`, `desktop_keys`, `mcp_servers`, `connection_prefs`, `autopilot_profiles`, `autopilot_targets` | Per row: a change on one side wins; on both, a deletion beats an edit, else the server's version. |

Removing a security record leaves a tombstone in the synced `meta`: a grant, a connected account, a token, a paired computer's key, an MCP server, or an approved Autopilot target. Adding the record again on purpose clears its tombstone. Every merge drops a record that has a tombstone, and so does every snapshot read, whether the server's, a base or a backup. So nothing removed on one phone comes back from another phone's copy, a stale base, the server-wins fallback, a restore or an import. Tombstones last 180 days. A phone whose base is older than that, such as one that was offline longer, does not use its base: whatever only that phone has is dropped unless the server has it too, and it is kept in the inert backup.

These are never synced, because they only mean something on one phone: `session`, `pending`, `handled`, `autopilot_suggestions`, `autopilot_rate`, `audit_snapshots`, installation keys and installation metadata.

Revisions only move forward. A server state older than the revision this phone agreed on, or older than an authentic revision it has seen, is refused with a notice; it is never merged and never uploaded over. A state that does not open for the revision it claims is refused the same way. The base can only be replaced by a newer revision's. Other phones' snapshots are first brought to this version's schema and data rules (a migration's rewrites apply to them too), so an app update alone is never a change. Without a usable base (an older version kept only a hash), the server's state wins, grants and modes only tighten, and this phone's copy is kept in a backup sealed with the device key. A notice says so. The backup is never uploaded. Only the user's explicit restore brings it back, and it goes through the same merge rules, never bringing back a grant. Sync problems never block sign-in; at most they show a banner the user dismisses.

Android native reminder and browser sign-in caches are encrypted under separate Keystore keys. iOS widget snapshots are encrypted under a device-only shared keychain key. Account changes discard screen models and decrypted views; logout removes account notifications and reminders.

On upgrade, legacy SQLite is encrypted durably before its plaintext files are removed. The old database had no trustworthy ownership boundary for its history, grants or integration credentials, so those mixed records remain in encrypted quarantine and are never assigned to whichever account signs in next. Previously stored recovery secrets can be recovered only through their verified server/user binding and successful decryption of that account's vault key. Integrations from the mixed legacy store need to be connected again under their owner.
