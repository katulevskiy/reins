## MCP protocol
- Latest revision **2026-07-28** (stateless core). Handshake removed: every request carries `params._meta` keys `io.modelcontextprotocol/protocolVersion`, `io.modelcontextprotocol/clientCapabilities`, `io.modelcontextprotocol/clientInfo`. New required method `server/discover` → `{supportedVersions, capabilities, serverInfo, instructions}`. Removed: `Mcp-Session-Id`, GET SSE stream, `ping`, `logging/setLevel`. Every result carries `resultType: "complete"` (or `"input_required"`). List results carry `ttlMs` and `cacheScope` (`"public"|"private"`); deterministic tool order. Errors: `UnsupportedProtocolVersion` -32022 with `data.supported[]`; `HeaderMismatch` -32020; unknown method → HTTP 404 + -32601. Servers SHOULD put `io.modelcontextprotocol/serverInfo` in result `_meta`.
- Streamable HTTP: single endpoint; each JSON-RPC message is a POST; client sends `Accept: application/json, text/event-stream`; server may answer plain `application/json`. Notifications → 202, no body. Required request headers: `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name` (for tools/call, resources/read, prompts/get; non-header-safe values `=?base64?…?=`). Server MUST validate headers against body (400 / -32020). Validate `Origin` (403 if present and invalid). Modern-only server: GET/DELETE → 405.
- Dual-era: a server MAY also accept legacy `initialize` (2025-11-25). Clients fall back to `initialize` only on a 4xx whose body is not a recognised modern JSON-RPC error. **Claude.ai still sends 2025-11-25 `initialize`** (observed 2026-09-26). **ChatGPT sends `server/discover` with `MCP-Protocol-Version: 2026-07-28`**, `User-Agent: openai-mcp/1.0.0`; answering 422 breaks it — use 400 with JSON-RPC body. Legacy needs `initialize`, `notifications/initialized` (202), `ping`, `tools/list`, `tools/call`; session ids optional (omit).
- Tool results: `content[]` (text, …), `isError: true` for tool-level errors the model sees, `structuredContent` (should also be serialized in a text block), unknown tool → -32602.
- Timeouts: **Claude 240 s per tool call**, result ≤ ~150,000 chars; **ChatGPT hard 60 s**. Tasks extension unsupported by both. Claude connectors are **IPv4-only**, egress 160.79.104.0/21.
- Rust SDK `rmcp` 3.5.0 is axum/tower based → write JSON-RPC over Rocket by hand.

## MCP authorization (2026-07-28)
- Protected Resource Metadata (RFC 9728) required; clients try the `WWW-Authenticate` `resource_metadata` pointer, then `/.well-known/oauth-protected-resource/<mcp-path>`, then root. Claude starts auth only on 401, uses only the first `authorization_servers` entry, and `resource` must exactly equal the URL the user entered. ChatGPT wants `resource`, `authorization_servers`, `scopes_supported`.
- 401: `WWW-Authenticate: Bearer resource_metadata="…", scope="…"`; 403 insufficient_scope. Don't put `offline_access` in resource scope (Claude adds it if the AS lists it).
- AS metadata RFC 8414 at `/.well-known/oauth-authorization-server` (path insertion when issuer has a path); `issuer` must match exactly. PKCE S256 mandatory; advertise `code_challenge_methods_supported: ["S256"]` (clients refuse if absent). RFC 8707: clients send `resource=<canonical MCP URL>` on authorize and token; servers MUST validate audience; canonical = lowercase scheme/host, no trailing slash. Token passthrough forbidden. RFC 9207: return `iss` in authorization response, advertise `authorization_response_iss_parameter_supported: true`.
- Client registration preference: pre-registered → **CIMD** (client_id is an HTTPS URL of a metadata doc) → DCR (deprecated, still allowed; DCR clients MUST send `application_type`). Claude uses CIMD only if AS metadata has `client_id_metadata_document_supported: true` AND `"none"` in `token_endpoint_auth_methods_supported`, else DCR. Claude Code CIMD: `https://claude.ai/oauth/claude-code-client-metadata`. ChatGPT CIMD client_id `https://chatgpt.com/oauth/client.json` or `https://chatgpt.com/oauth/{callback_id}/client.json`, auth `none` or `private_key_jwt`.
- Redirect URIs: Claude hosted `https://claude.ai/api/mcp/auth_callback`; Claude Code `http://localhost:<any>/callback`, `http://127.0.0.1:<any>/callback` (port-agnostic); ChatGPT `https://chatgpt.com/connector_platform_oauth_redirect` (only if AS advertises + returns `iss`), else `https://chatgpt.com/connector/oauth/{callback_id}`.
- Claude: discovery/registration/token endpoints must answer < 10 s (refresh < 30 s); `/token` accepts form-urlencoded; `invalid_grant` for dead refresh tokens; rotate refresh tokens for public clients; refresh on 401 or 5 min before expiry.

## UniFFI
- Latest 0.32.2 (2026-09-23). `async fn` → Kotlin `suspend fun` (kotlinx-coroutines ≥ 1.6; latest 1.11.0). `#[uniffi::export(async_runtime = "tokio")]` with Cargo feature `uniffi/tokio` (wraps futures in async_compat); its long-term support is uncertain — alternative: own static tokio Runtime and `spawn` onto it, awaiting the JoinHandle.
- Foreign traits: `#[uniffi::export(foreign)]` (Kotlin-implemented) or `#[uniffi::export(rust, foreign)]`; async methods work with `#[uniffi::export]` placed outside `#[async_trait::async_trait]`; trait must be `Send + Sync`, methods return `Result`. No cancellation.
- Proc-macros are the primary path; library mode auto-detected. Bindgen: `uniffi-bindgen generate <lib.so> --language kotlin --out-dir …` (build a `uniffi-bindgen` bin in-crate: `fn main() { uniffi::uniffi_bindgen_main() }` with feature `cli`).
- Android: JNA ≥ 5.12.0 as `net.java.dev.jna:jna:5.19.1@aar`; attach tokio worker threads to the JVM if Rust calls back into Kotlin (JNA handles attach for callbacks it invokes). Build: plain cargo-ndk 4.1.2 + Gradle Exec task: `cargo ndk -t arm64-v8a -t x86_64 -o src/main/jniLibs build --release`. 16 KB page size: NDK r28+ or `-Wl,-z,max-page-size=16384`. Installed NDKs here: 25.1, 27.0, 27.2 → use 27.2 with the linker flag.

## Gmail API
- Scopes: `gmail.readonly` (restricted), `gmail.send` (sensitive). `gmail.metadata` also restricted and can't use `q`. Restricted scopes need verification + annual CASA for public apps.
- Testing mode: ≤100 test users and **7-day refresh token expiry** (External). "In production, unverified": warning screen, 100-user lifetime cap, no 7-day expiry.
- Endpoints: `GET https://gmail.googleapis.com/gmail/v1/users/me/messages?q=&maxResults=&pageToken=` → ids only; `GET …/messages/{id}?format=metadata&metadataHeaders=From&metadataHeaders=To&…` or `format=full`; `POST …/messages/send` body `{"raw": base64url(RFC 2822), "threadId"?}`. Batch endpoint `https://gmail.googleapis.com/batch/gmail/v1` (≤100, recommend ≤50). Quota: 6,000 units/min/user; get = 20 units, list = 5, send = 100 (page updated 2026-09-10).
- Android auth: custom URI schemes unsupported for Android clients; use **Google Identity Services `AuthorizationClient`** (`play-services-auth` 22.0.0): `Identity.getAuthorizationClient(ctx).authorize(AuthorizationRequest.builder().setRequestedScopes(listOf(Scope(...))).build())` → `AuthorizationResult` with `accessToken` (1 h) or `hasResolution()` → launch `pendingIntent` for consent. Subsequent calls return fresh tokens silently. Needs an Android OAuth client (package + SHA-1) in the project. [UNCERTAIN] silent `authorize()` from a background worker — test; fall back to notification asking the user to open the app.

## Android background
- FCM high-priority data messages can wake the app; deprioritized if they don't lead to user-visible notifications. `onMessageReceived` has a short window → enqueue an **expedited WorkManager job** (2.12.0) immediately (FCM high priority grants a brief quota exemption). Check `remoteMessage.priority == RemoteMessage.PRIORITY_HIGH`.
- `shortService` FGS (~3 min, only `FOREGROUND_SERVICE` permission) can start from background only with an exemption such as high-priority FCM; must stop in `onTimeout()`.
- UnifiedPush 3.3.5 viable later as an FCM alternative.
