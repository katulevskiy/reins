# Decisions v2 · O5 Compliance packaging: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** an org's audit log leaves Reins in forms an auditor and a security team can use without trusting Reins:
- the open-source `reins-audit` program, released, verifies an export and turns it into SOC 2 and ISO 27001
  evidence;
- the audit chain streams to the org's SIEM (Splunk, Datadog, Elastic, Sentinel) and to S3 or GCS with object lock;
- checkpoints are timestamped by an external RFC 3161 authority;
- old events are pruned down to a signed checkpoint, by tier;
- the master key can be wrapped by the customer's own KMS (AWS KMS, GCP Cloud KMS, Azure Key Vault);
- the executor ships as release binaries and a container image, with a configuration reference.

The program's acceptance closes here: a pilot org provisioned and deprovisioned end to end, its export verified by
`reins-audit verify`, tampering caught.

**Architecture:**
- **`reins-audit` (Apache-2.0, offline).** O2's verifier is kept as it is. Add an `evidence` module (pure: verified
  events → a per-control report) and a `cli` module (`verify`, `report`), so `main.rs` is a thin wrapper and the e2e
  suite runs the exact code path of the binary. A report is only ever made from an export that verified.
- **The server** (`src/api/reins/org/`, all behind `REINS_ORGS_ENABLED`):
  - `audit.rs` gains pruning to a checkpoint anchor and a non-recording segment export;
  - `witness.rs`: RFC 3161 timestamps of stored checkpoints, asked by the sweeper (async, never inside a
    transaction), replacing O2's unused synchronous `Witness` seam;
  - `sinks/`: audit streaming, configured like O3's channels (secrets posted and sealed by one admin, turned on by a
    two-person device-signed change `AdminAction::SetAuditSink`), pushed by the sweeper from a per-sink cursor;
  - `sigv4.rs`: AWS Signature V4, shared by the S3 sink and the AWS KMS adapter;
  - `kms_byok.rs`: the 32-byte master key stored *wrapped* by a cloud KMS and unwrapped once at launch; without it
    the org features fail closed (no fallback to a fresh local key);
  - console: evidence report and checkpoint/timestamp downloads, the streaming page.
- **Release:** a new `audit-tools` job builds `reins-audit` and `reins-executor` as static musl binaries (x86_64,
  aarch64), and an `executor-image` job builds `ghcr.io/<owner>/reins-executor` from them (`FROM scratch`). Neither
  job reads a secret; `publish` waits for both and tags the image with the server's.

**Tech stack:** Rust 1.98.1 (`ring`, `serde`, `reqwest`, `x509-parser`'s DER parser, `openssl` for MD5 only,
`jsonwebtoken` for the GCP service-account assertion), Rocket and Diesel (sqlite, mysql, postgresql), GitHub Actions,
Docker buildx.

**Spec:**
- `docs/design/decisions-v2/06-trust-and-compliance.md` §3 (keys, BYOK/HSM), §4 (retention), §5 (audit log:
  integrity, export), §7 (SOC 2 mapping);

## Global Constraints

- Everything server-side is off unless `REINS_ORGS_ENABLED`; no route, sweep or launch step runs without it.
- Personal mode is untouched: no Personal data enters an org chain, a sink or a report.
- The audit chain is never rewritten: pruning deletes only events *below* a stored signed checkpoint, which stays.
- Sink and KMS secrets are sealed under the tenant data key (sinks) or never stored in clear (KMS master); they are
  never logged and never shown back.
- Turning a sink on is a two-person change with device signatures (06 §3: it decides where audit goes).
- Outbound requests to admin-given URLs go through `api::reins::outbound` (https, public addresses, no redirects).
- Release: signing and secrets only in `publish` and later, on main; new jobs have `contents: read` (plus
  `packages: write` for the image) and finish before `publish` fetches the release key.
- Toolchain: `PATH=$HOME/.rustup/toolchains/1.98.1-x86_64-unknown-linux-gnu/bin:$PATH cargo clippy -p <crate> -j 4 --
  -D warnings`; cargo `-j 4`; `CARGO_TARGET_DIR` inside the worktree; never `/tmp`.
- UI copy short; real icons only (the console uses inline SVG icons already); never emoji.
- Commits authored by Daniel Katulevskiy, signed, no AI mention.

## Review Focus

1. **A report on a forged export.** `reins-audit report` on an export that fails verification must print nothing but
   the failure and exit 1 (Task 2 test `report_refuses_an_unverified_export`).
2. **A sink as an SSRF or exfiltration path.** An admin-given Splunk/Elastic/Sentinel/S3 URL to a private address or
   over http must be refused, and a reinstalled sink must turn off and lapse pending enables (Task 6 tests
   `a_private_or_http_url_is_refused`, `reinstalling_turns_a_sink_off`).
3. **Pruning that loses the anchor.** After a prune, an export must start from the kept checkpoint and still verify;
   with no checkpoint old enough nothing is pruned (Task 3 tests).
4. **BYOK falling back silently.** With a cloud provider configured and the unwrap failing, `kms()` must error, never
   create a local key (Task 7 test `a_failed_unwrap_never_falls_back_to_a_local_key`).
5. **A sink cursor running ahead of delivery.** A failed or partial push must not advance the cursor; Elastic
   duplicates (409) count as delivered (Task 6 tests).
