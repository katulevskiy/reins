# Decisions v2 · P7 Guardianship and the Family tenant: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** guardianship in two strengths (08 R7):
- **Personal guardianship** completes P6's cooperative Guardian Circle with the rest of 04 §4:
  - notice periods;
  - minor accounts;
  - ward visibility;
  - an opt-in weekly digest;
  - tamper-evident **guardian notices** when the ward ends or pauses it, resets or deletes the account, or changes the
    roster.
- **The Family tenant** is an O1 org tenant of tier `Family`, for enforceable guardianship. The guardians are the org:
  they connect the child's accounts and the family's executor holds the credentials, so a child's agents act only
  through the family's connections (O2).

**Architecture:**
- **Part A (Personal, PR 1, on P6).**
  - P6 already has `CircleKind::Guardian` as a `required` reviewer that only the guardian fills, so no permit, Auto or
    Bypass satisfies it.
  - P7 adds `Terms.guardian: Option<GuardianTerms>` (notice days, minor, digest), signed in the arrangement at setup.
    Later changes go through P6's signed `LinkChange`, which gains a `guardian` payload: minor proposed or accepted,
    digest on or off, end requested, end consented.
  - **Ending.** The ward's end is an `EndRequest` with `effective_at = at + notice`. Both phones keep the arrangement in
    force until then. A minor's end waits for the guardian's signed consent.
  - **The server is blind, but it sees routing metadata** (08 R8, accepted):
    - it stores the change history and `effective_at` in clear;
    - it writes **guardian notices** for what it observes: account reset or deletion (before the rows go), roster
      appends, and changes on Guardian links.
  - **The guardian's phone checks** each signed change against the terms in its own sealed copy, and roster changes
    against the chain (P6's `peer_keys`). Anything early, unsigned or uncheckable shows as such ("Ended early",
    "Reported by the server").
- **Part B (Family, PR 2, on O1 and O2).**
  - `Tier::Family` is an O1 tenant with no domain and no IdP. Members join by an invitation bound to an exact email,
    and only with a new account (08 R6).
  - Guardians hold `OrgOwner`, `SecurityAdmin`, `ConnectionAdmin` and `Approver`. Children are `Member`s with a
    `minor` flag.
  - The policy is an O2 `OrgPolicy` built by `family_baseline()`. The child's accounts are connected by a guardian
    through an OAuth flow the family's **executor** completes, so the refresh token lives only in the executor.

**Tech stack:** Rust 1.98.1 (`reins-proto`, `reins-policy`, `reins-core`, `reins-executor`, the server on
Rocket/Diesel), UniFFI, Kotlin/Compose (Robolectric), Swift/SwiftUI (XCTest). Apple `DeclaredAgeRange` and Google Play
Age Signals behind one seam.

## Global Constraints

- The program plan's constraints hold. In particular:
  - **Auto never denies.**
  - **Notifications are only for things the user must act on.**
  - The 08 R4 floor is a hard review.
  - **Personal mode stays end to end:** the server never stores request bodies, packets, answers or terms in clear.
- **04 §4, verbatim:**
  - "Ending a guardianship starts a notice period the ward chose at setup (0, 3 or 7 days, shown up front), and
    notifies the guardian. During it, the obligations stay."
  - "Adults can always leave: the notice period caps at 7 days, and there's no 'permanent' option."
  - "If the ward's account is marked as a minor's … leaving needs the guardian's consent."
  - "No secret reading: the guardian's view is the request card within scope. No inbox, no chat history, no vault."
- Redaction is **summary** for Guardian (04 §5; P6's `default_for`). The digest of Auto decisions in scope is **opt-in
  by the ward** and weekly (04 §1, §4).

  checks make leaving early *visible*, not impossible. Enforcement is claimed only for Family.
- **The ward's own guardian slot can't be removed silently.** The ward can't pause a Guardian link (P6 lets owners
  pause). The guardian can pause or leave at any time (04 §3).
- 08 R6: a Family invitation never binds an existing account, and an org (a family) never learns a Personal profile
  exists.

## Review Focus

1. **A guardian coercing an adult:** marking them a minor alone, a notice over 7 days, or "permanent".
   - A minor mark needs the ward's signed acceptance, with an age signal where the platform has one.
   - Notice days are only 0, 3 or 7.
   - Tests: `circle::tests::notice_days_are_0_3_or_7` (Task 1), `guardian::a_guardian_cannot_mark_an_adult_minor_alone`
     (Task 4).
2. **A ward ending early:**
   - an end with `effective_at` before `at + notice`;
   - a minor's end without consent;
   - a ward's pause;
   - a link that vanished from the server.

   Obligations stay on a cooperating ward's phone, and the guardian's phone shows each of these as "Ended early" or
   "Paused by Sam". Tests: `guardian::an_early_end_is_flagged_to_the_guardian`,
   `guardian::a_ward_cannot_pause_a_guardian` (Task 4).
3. **The server forging or hiding notices.** It can drop or delay them. It can't forge a roster change or a signed
   change: the guardian's phone checks both, and labels the rest "Reported by the server". Test:
   `guardian::server_notices_are_verified_or_labelled` (Task 4).
4. **A ward escaping by reset or deletion.** The guardian is told before the rows go. Tests:
   `guardian_notices::tests::reset_notifies_every_guardian`, `a_deleted_account_notifies_before_erase` (Task 2).
5. **A Family invitation capturing an existing account,** or used by someone else. Invites bind to the exact email,
   are single use and expire. An address with an account is refused without naming anyone. Tests:
   `family::tests::an_existing_account_is_never_captured`, `invites_are_single_use_and_bound_to_the_email` (Task 9).

## Part A — Personal guardianship (PR 1, after P6 merges)

### Task 1: Guardian terms and changes in the protocol

**Files:** modify `crates/reins-proto/src/circle.rs` (P6's; inline tests), `canon.rs` (context `CIRCLE_GUARDIAN`) and
`pairing.rs` (`PushKind::Guardian`, additive and last).

**Interfaces (Produces):**
- `Terms.guardian: Option<GuardianTerms>` (serde default, skip none). `Arrangement::validate()` requires it exactly
  when `kind == Guardian`.
- `struct GuardianTerms { notice_days: u8, minor: Option<MinorMark>, digest: bool }`, with `pub const NOTICE_DAYS: [u8;
  3] = [0, 3, 7]`. At setup, `digest` is false and `minor` is set only with the ward's acceptance (Task 4).
- `struct MinorMark { source: AgeSource, at: i64 }`:
  - `enum AgeSource { Platform { kind: AgePlatform, upper: Option<u8> }, GuardianAndWard }`;
  - `enum AgePlatform { AppleDeclaredAgeRange, GooglePlayAgeSignals }`.
- `LinkChange.guardian: Option<GuardianChange>` (serde default). With it, `state` stays `Active`, except for
  `EndConsent`.
- `enum GuardianChange`:
  - `MinorProposed` (by the helper);
  - `MinorAccepted { mark: MinorMark }` (by the owner);
  - `Digest { on: bool }` (by the owner);
  - `EndRequested { effective_at: i64 }` (by the owner);
  - `EndConsented { request_at: i64 }` (by the helper; comes with `state: Ended`).
- `pub fn guardian_effective(terms: &GuardianTerms, minor_now: bool, requested_at: i64) -> Option<i64>`: `None` for a
  minor, else `requested_at + notice_days × 86 400`.
- `pub fn check_guardian_change(terms: &GuardianTerms, minor_now: bool, c: &LinkChange) -> Result<(), CircleError>`:
  - it refuses an owner `EndRequested` whose `effective_at` isn't `guardian_effective(...)`;
  - a minor's `EndRequested` is refused (they ask with `EndRequested { effective_at: i64::MAX }`, a request waiting
    for consent);
  - an owner `state: Paused` on a Guardian link is refused;
  - a `MinorProposed` must come from the helper, and `MinorAccepted` and `Digest` from the owner.
- The helper ending (`by: Helper, state: Ended`, without `guardian`) stays valid at once: the guardian leaves.
- `enum GuardianNoticeKind { AccountReset, AccountDeleted, RosterChanged { reason: RosterReason, epoch: u64 },
  LinkChanged { change: SignedChange } }` and `struct GuardianNotice { id, link, kind, at }`, both server-written.

**Interfaces:**
- `pub enum OAuthProvider { Google, Github }` in `reins_proto::managed`. `pub struct ConnectJob { member: String,
  provider: OAuthProvider, phase: ConnectPhase /* Begin | Finish { code: String, state: String } */ }`.
- **Begin** (a guardian with `ManageConnections`, in the console):
  - the server queues `Connect{Begin}`;
  - the executor makes a PKCE verifier and a `state`, keeps them in `state_dir/connect/<state>` (10 min), and returns
    the authorization URL in its receipt. It holds the OAuth client id and secret (`ExecutorConfig.user_oauth`);
  - the server redirects the guardian's browser there.
  - Google scopes are the existing Gmail and Calendar connector scopes; GitHub's are `repo` and `read:user`.
- **Finish:** the provider redirects to `GET /reins/org/family/oauth/callback?code&state`. The server queues
  `Connect{Finish}` and never redeems the code: it can't, without the verifier and the client secret. The executor
  exchanges it and stores the refresh token in `user_tokens.json`, encrypted with AES-256-GCM under a key derived by
  HKDF from its key file (info `reins/user-tokens/v1`), file mode 0600. It receipts `{account}`, and the server marks
  the row `connected`.
- `UserOAuthConnector` implements O2's `Connector`. `run(member_email, tool, args)` refreshes that member's token (and
  only that member's) and calls the same Gmail, Calendar or GitHub endpoints as O2's connectors, with the same minimal
  results.
- Revoke: a guardian's revoke queues `Connect`-revocation. The executor revokes upstream (Google `oauth2/revoke`;
  GitHub `DELETE /applications/{client_id}/grant`) and deletes the token. Deprovisioning a member revokes theirs (O2's
  revocation queue).
- Child agents pair to the Family profile (O1's picker), so R6 holds: a Personal connection of the same person never
  reaches the family's tools.
