# Decisions v2 · O4 Policy as code, simulation and staged rollout: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** an org policy change goes from a PR on `acme/reins-policy` (or a console draft):
- through simulation on the org's retained history;
- to two Security admins' device-signed approval;
- then to a staged rollout (pilot group → 25% → everyone) with automatic rollback.

Every decision pins the version it used. Personal mode gets the same simulation as a preview when the owner changes
the matrix or a rule (02 §4).

**Architecture:**
- **One source format.** A TOML policy repo compiles deterministically into O2's `reins_policy::org::OrgPolicy`, in a
  pure module `reins_policy::source`. It also renders an `OrgPolicy` back to TOML, so console drafts and O3's
  templates export to the repo.
- **One evaluator.** O2's `evaluate_managed` is split into analysis and evaluation (`evaluate_analyzed`), with no
  behaviour change. The decision service retains each request's body-free analysis as decision metadata, and
  `reins_policy::simulate` replays drafts over it with the **same** `evaluate_analyzed` the live service and the
  executor run (08 R5). The Personal flavour replays `matrix::evaluate` on the phone.
- **The server** adds:
  - the policy-repo binding (GitHub webhooks → compile → simulate → Check Run);
  - simulation evidence bound to the draft hash, required by O2's `ActivatePolicy`;
  - a rollout controller.
- **Signed rollouts.**
  - At activation the issuer key pre-signs every stage and the rollback as `Envelope{kind: Rollout}`.
  - The controller publishes the next stage when the dwell passes cleanly, and the rollback on a guard breach.
  - The executor refuses a decision whose snapshot isn't the member's effective one under the newest signed rollout it
    holds.

**Tech stack:** Rust 1.98.1 (`toml`, `serde`, `sha2`), the server (Rocket, Diesel), `reins-executor`, UniFFI,
Kotlin/Compose, Swift/SwiftUI.

**Spec:**

## Global Constraints

- The program plan's constraints hold.
- **Determinism (02 §3 rule 6).**
  - "The same inputs and policy snapshot always give the same decision." Simulation calls the exact evaluation the live
    path calls, never a copy.
  - "The snapshot's hash is recorded with every decision"; "Effective-version pinning is recorded in every decision"
    (05 §7.3).
- **Authoring.**
  - "Policy authors must run it before saving (Managed mode) and see it as a preview (Personal mode)" (02 §4).
    Activation needs a simulation report for exactly that revision's hash, at most 24 h old.
  - "Activating a policy takes two Security admins" (08 R5), with O2's device signatures. There's no sole-holder
    exception, except `Tier::Family` (P7): every guardian holding `ActivatePolicy`, at least one.
  - A Policy author drafts and simulates and can't activate. An admin can't approve their own change (05 §3).
- **Rollout (05 §7.3):** "a pilot group, then 25%, then everyone, with automatic rollback if the ask rate or SLA crosses
  a set threshold." Executors pick up a change within a minute.
- **The policy repo is input, not authority.** A merge creates a pending activation only. Webhooks are verified
  (`X-Hub-Signature-256`). Content is capped at ≤ 200 files and ≤ 1 MiB.
- **Simulation output names no request bodies.**
  - The retained analysis is decision metadata (06 §4: effects, zones, levels, as in 06 §5.1's event), never bodies.
  - Changed samples are request ids; opening one is an audited Auditor or Security admin read.
- **Personal preview stays on the phone.**
- Migrations for sqlite, mysql and postgresql. GitHub is never called in tests (wiremock).
- Builds:
  - `source ~/Documents/dev/tmp/dv2-o4/env.sh` (`CARGO_TARGET_DIR`, `XDG_CONFIG_HOME` and `TMPDIR` under
    `~/Documents/dev/tmp/dv2-o4/`); cargo `-j 4`, narrow `-p`;
  - pinned clippy (`target-198`); `cargo fmt`; never `/tmp`;
  - Android and iOS as in the program plan.
- **Console files.** O4's pages go in `src/api/reins/org/console_policy.rs` and `console_policy_pages.rs`, and O2's
  `/<org>/policy` page links to them. O3 owns `console_routing.rs`.
- UI: short copy, real icons, never emoji. Commits and PRs never mention AI.

## Review Focus

1. **Simulation and live disagreeing:** a copied evaluator, another clock, other facts. Replaying retained history with
   the **active** policy must reproduce the recorded outcomes. A mismatch is reported as `drift` and blocks activation.
   Test: `simulate::tests::the_active_policy_reproduces_history` (Task 2).
2. **A compromised decision service choosing the looser version** for a request: the candidate for a non-cohort
   member, or the old stable after a rollback.
   - The executor recomputes the member's effective hash from issuer-signed rollouts and refuses a mismatch.
   - Publishing a pre-signed stage early only moves forward a rollout two admins approved. This is accepted and stated
     in `security-model.md`.
   - Test: `reins-executor` `verify::tests::a_hash_outside_the_members_cohort_is_refused` (Task 7).
3. **A Policy author activating alone:** by merging the repo PR, by re-posting the activation, or as the only Security
   admin. Each is refused. Tests: `policy_repo::tests::a_merge_only_creates_a_pending_activation` (Task 5);
   `activation::tests::a_sole_security_admin_cannot_activate`, `the_proposer_cannot_approve` (Task 4).
4. **Rollback flapping or acting on noise.** Guards act only with at least `min_decisions` in both cohorts; a member's
   cohort is stable for the whole rollout; a rollback is terminal. Tests: `small_samples_never_roll_back_or_advance`,
   `a_member_never_flips_within_a_rollout` (Task 6).
5. **A draft changed after it was simulated** (a new push to the PR, a console edit). The evidence binds to the hash,
   so activation needs a fresh simulation. Test: `activation::tests::a_changed_draft_needs_a_new_simulation` (Task 4).

### Task 1: The policy source format

**Files:** create `crates/reins-policy/src/source.rs` and `crates/reins-policy/tests/fixtures/policy_repo/` (a sample
repo); modify `lib.rs` and `Cargo.toml` (`toml`, workspace version).

Format (every table `deny_unknown_fields`):
```toml
# reins-policy.toml
version = 1
org = "acme"
explain = "Acme policy"
cell_review = { reviewers = "requester", class = "instant", window = "2m" }
[rollout]
pilot_group = "Platform"
stages = ["pilot", "25%", "100%"]
dwell = "24h"
guards = { max_ask_rate_delta_pp = 2.0, max_median_ttd = "30m", min_decisions = 50 }

# matrix.toml (cells per zone, as P2's Matrix), facts.toml (P2 Facts), posture.toml (O2 PostureRule)

# rules/prod.toml
[[rule]]
id = "prod-deploys"
explain = "Acme requires Security to approve production deploys"
when = { resource = "acme/prod-*", effects = ["Infra", "GitPush"], levels = ["L2", "L3"] }
review = { reviewers = "any of Security", quorum = 1, class = "deferred", window = "4h" }
```
- A rule has exactly one of `deny = true`, `permit = true` or `review = {…}`.
- O3's filters (`members`, `require_reason`, `outside_hours`, `min_amount`, `new_party`) and `escalate` are accepted
  once O3 has merged, and refused before with "needs O3".

**Interfaces (Produces):**
- `pub struct Compiled { pub policy: OrgPolicy, pub hash: String, pub plan: RolloutPlanSource }`, where
  `RolloutPlanSource { pilot_group: Option<String>, stages: Vec<StageSource>, dwell_secs: u64, guards: Guards }`.
  Pilot members are resolved at activation (Task 4).
- `pub struct SourceError { pub file: String, pub line: usize, pub message: String }`.
- `pub fn compile(files: &BTreeMap<String, String>) -> Result<Compiled, Vec<SourceError>>`. It:
  - reads `reins-policy.toml`, `matrix.toml`, `facts.toml`, `posture.toml` and `rules/**/*.toml`, ignoring other
    files;
  - sorts rules by id;
  - runs O2's `OrgPolicy::validate()`, mapping errors to the rule's line.
- `pub fn parse_reviewers(expr: &str) -> Result<Reviewers, String>`:

- `pub fn render(policy: &OrgPolicy, plan: &RolloutPlanSource) -> BTreeMap<String, String>`: one rules file per id

### Task 3: Signed rollouts

**Files:** create `crates/reins-proto/src/rollout.rs`; modify `lib.rs` and `managed.rs` (`EnvelopeKind::Rollout`,
additive and last).

**Interfaces (Produces):**
- `pub enum Stage { Pilot { members: Vec<String> /* sorted user uuids */ }, Percent(u8), All }`.
- `pub struct Guards { pub max_ask_rate_delta_pp: f64, pub max_median_ttd_secs: u64, pub min_decisions: u32 }`.
  `Default` is 2.0, 1800 and 50.
- `pub struct RolloutPlan { pub stages: Vec<Stage>, pub dwell_secs: u64 /* default 86 400 */, pub guards: Guards }`.
- `pub struct Rollout { pub org: String, pub rollout_id: String, pub seq: u32, pub stable: String, pub candidate:

  JSON.
- `pub fn in_cohort(rollout_id: &str, member: &str, stage: &Stage) -> bool`:
  - `Pilot`: membership;
  - `Percent(p)`: `u16::from_be_bytes(sha256(rollout_id ‖ 0x00 ‖ member)[0..2]) % 100 < p`;
  - `All`: true.
- `pub fn effective(rollouts: &[Rollout], member: &str, active: &str) -> String`. Per `rollout_id` it takes the highest
  `seq`, and a `terminal` rollback wins over any stage. The result is `candidate` when in the cohort, else `stable`,
  and with no rollout the `active` hash.
- Seq layout at activation: stages are `1..=n`, and the rollback is `n + 1` with `terminal`. When the last stage
  (`All`) completes, the candidate becomes the active policy and the rollout closes.

### Task 6: The rollout controller

**Files:** create `src/api/reins/org/rollout.rs`; modify `org/sweeper.rs` (O2's: `rollout::tick` every 60 s),
`org/decisions.rs::submit` (evaluate with the effective version), `org/executor_api.rs` (`GET
/reins/org-exec/rollouts`), and `reins_proto::managed::DecisionRecord` (`rollout: Option<(String, u32)>`, serde
default).

**Interfaces:**
- `pub fn effective_policy(c, org, member, now) -> Result<(OrgPolicy, String /* hash */, Option<(String, u32)>),
  OrgError>`, using Task 3's `effective`. `submit` uses it; it records `snapshot` and `rollout` on the request and in
  `DecisionRecord` (pinning) and in the audit detail.
- `pub fn tick(c, org, now) -> Result<(), OrgError>`, for each `running` rollout:
  1. Measure the current stage since `stage_started_at`, per cohort:
     - the ask rate (share of `Review`);
     - the median time to decision (O3's `sla::median_ttd(members)` when present, else
       `median(decided_at − created_at)` over reviewed requests).
  2. **Breach** (both cohorts ≥ `min_decisions`, and the candidate ask rate − stable > `max_ask_rate_delta_pp`, or the
     candidate median > `max_median_ttd_secs`):
     - publish the rollback seq; state `rolled_back`; the candidate revision goes back to `draft`;
     - `policy.rolled_back {why, numbers}`;
     - notify Security admins.
  3. **Dwell passed with no breach:** publish the next seq and record `policy.stage_advanced`. After `All`, `complete`:
     the candidate is `q_activate`d and the old one retired.
  4. **Too few decisions:** wait. The console shows "Waiting for N more decisions".
- `POST /reins/org/<org>/rollouts/<id>/{pause,resume,advance,rollback}` needs `ActivatePolicy`. One person suffices,
  because the stages were approved at activation, and `rollback` is always allowed. Each is audited.
- `GET /reins/org-exec/rollouts` (executor-signed request, O2 auth) returns the published `Rollout` envelopes of
  running and recently finished rollouts (≤ 7 days).
