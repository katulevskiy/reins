# Decisions v2 · O3 Routing, on-call, Slack/Teams approvals and templates: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the right person approves, fast:
- org review obligations name **relationships** (the requester's manager, the repo's code owners, a resource's owner)
  and **on-call** schedules (PagerDuty, Opsgenie, Incident.io) next to O2's groups and roles;
- an unanswered obligation **escalates** along a chain;
- **SLA reports** show time to decision per group;
- **Slack and Teams** carry L0–L2 reviews to a signed web approval (SSO plus a device-bound passkey);
- the four remaining **templates** of 05 §7.2 join O2's Developer baseline.

**Architecture:**
- Built on O2's planned shapes: `reins_policy::org`, `reins_proto::managed`, the decision service
  (`org/decisions.rs`), reviews (`org/reviews.rs`) and `reins-executor`.
- **Resolution.**
  - O2's `Reviewers` gains relationship and on-call variants. At `submit`, the decision service resolves each
    obligation to a member set from verified sources only: the directory, a read-only GitHub App, on-call APIs.
  - It stores the result on the request and puts it into the countersigned `DecisionRecord` (`resolved`).
- **Eligibility for the executor (08 R5).**
  - Group, Role and Manager are checked against the issuer-signed roster; Manager is added to it.
  - Code owners, on-call and resource owner are dynamic, so the executor accepts the decision service's countersigned
    resolution for them. The approver must still be a roster member with a valid device or passkey signature. This
    trust statement is written into `security-model.md`.
- **Escalation.** O2's single expiry becomes a per-obligation chain of steps, swept in `decisions::sweep`.
- **Web approval.** It is a WebAuthn assertion over a challenge derived from O2's `review_message`. Confirmed passkeys
  are listed in the signed roster, so the executor verifies them like device keys.
- **Channels.** Slack and Teams are notifications with a link, never a decision path.
- **Templates** are `OrgRule` builders. O4's source format renders them.

**Tech stack:** Rust 1.98.1 (Rocket, Diesel for sqlite/mysql/postgresql, reqwest, `webauthn-rs` 0.5 (already in the
workspace), `ring`, `chrono-tz` (already in the workspace), `jsonwebtoken` for Bot Framework tokens), UniFFI,
Kotlin/Compose, Swift/SwiftUI.

## Global Constraints

- The program plan's constraints hold:
  - mandatory deny and review win;
  - unknown facts never widen;
  - authority is proven, never claimed.
- **Verified sources only** (05 §7.1):
  - managers come from the directory (SCIM `manager_email`), or from a Security admin on the Team tier, which has no
    SCIM;
  - code owners come from the default branch through the org's read-only GitHub App;
  - on-call comes from the provider's API;
  - nothing comes from the agent.
- **No self-approval.** `exclude_requester` stays on by default (05 §6), whatever set the requester falls in.
- **Channels.** "Slack and Teams buttons can be enabled for L0–L2 reviews. They open a signed web approval that
  requires SSO plus device-bound passkeys. L3 always needs the app." (05 §6.)
- **Escalation.** "Each obligation has a window; on expiry it escalates (backup group, manager, then Security admin);
  SLA reports show time to decision per group" (05 §6). Escalation adds reviewers; it never removes any.
- **Notifications only for action.** A reviewer is notified when an obligation reaches them, on arrival or on
  escalation to them, plus P4's 50% and 90% reminders. Resolutions and automatic outcomes notify nobody. `urgent`
  obligations break quiet hours (03 §5.2).
- **No bodies in third-party channels.** A Slack or Teams message carries one line at the `minimal` level: requester,
  agent, effect kind, resource name, level and what it needs. The card is in the web approval or the app, under
  retention.
- Changes to channels, on-call sources, the GitHub reader and managers go through two-person `admin::propose` with
  device signatures (05 §3, 06 §3).
- Migrations for sqlite, mysql and postgresql; MySQL ids use `utf8mb4_bin`. External APIs are never called in tests
  (wiremock, or the loopback mock server).
- Builds:
  - `source ~/Documents/dev/tmp/dv2-o3/env.sh` (`CARGO_TARGET_DIR`, `XDG_CONFIG_HOME` and `TMPDIR` under
    `~/Documents/dev/tmp/dv2-o3/`); cargo `-j 4`, narrow `-p`;
  - pinned clippy `PATH=$HOME/.rustup/toolchains/1.98.1-x86_64-unknown-linux-gnu/bin:$PATH CARGO_TARGET_DIR=target-198
    cargo clippy -p <crate> -j 4 -- -D warnings`; `cargo fmt`; never `/tmp`.
- UI: short copy, real icons, never emoji, the Next look. Commits and PRs never mention AI.
- **Console files.** O3's pages are `src/api/reins/org/console_routing.rs` and `console_routing_pages.rs`. O4 owns

## Review Focus

1. **An obligation nobody can satisfy:** no manager on record, owners unlinked, the on-call API down, or only the
   requester eligible. It escalates and, after the last step, expires as "not approved". It never auto-approves and
   never falls to the requester. Test: `routing::tests::an_unsatisfiable_obligation_escalates_never_widens` (Task 3).
2. **A Slack or Teams link opened by someone else,** whether forwarded or posted in a shared channel. The token binds
   to one member and one request and works once. The session must be that member's SSO session, and the passkey one
   they registered and confirmed on their enrolled phone. Test:
   `web_approval::tests::a_token_works_once_for_its_member_only` (Task 7).
3. **A synced (not device-bound) passkey, or a web approval of L3.** Both are refused, by the server and again by the
   executor. Tests: `web_approval::tests::a_synced_passkey_is_refused`, `l3_is_refused_on_the_web`;
   `reins-executor` `verify::tests::passkey_approvals_are_refused_for_l3` (Task 7).
4. **A decision service resolving a relationship to an accomplice.**
   - For Manager, the executor checks the issuer-signed roster.
   - For code owners and on-call, it accepts the countersigned resolution. Every resolution is audited with its
     source evidence (`review.resolved {obligation, members, source, evidence_hash}`).
   - Tests: `reins-executor` `verify::tests::a_manager_not_in_the_roster_is_refused`;
     `routing::tests::every_resolution_is_audited_with_evidence` (Tasks 3, 7).
5. **Forged inbound webhooks:** a Slack payload without a valid `X-Slack-Signature`, a stale timestamp, or a Teams
   activity with a bad JWT. They are refused and change nothing; inbound payloads never decide anything. Tests:
   `slack::tests::signatures_are_verified_and_replays_refused` (Task 8),
   `teams::tests::activities_need_a_valid_bot_framework_token` (Task 9).

### Task 4: The GitHub reader and code owners

**Files:** create `src/api/reins/org/github_reader.rs` (if O4 hasn't) and `src/api/reins/org/routing/codeowners.rs`.

**Interfaces:**
- **`github_reader.rs`**, shared with O4. This is the exact interface either plan creates.
  - It is the org's second, read-mostly GitHub App. Permissions: `contents: read`, `members: read`, `pull_requests:
    read`, `checks: write` (O4). It is installed by a Connection admin. The App's key never reaches the executor, and
    the executor's App key never reaches the server.
  - `pub struct GithubReader { … }`.
  - `pub fn for_org(c, org: &str) -> Result<Option<GithubReader>, OrgError>`.
  - `pub async fn get_json(&self, path: &str) -> Result<serde_json::Value, String>`, plus `post_json`, `patch_json`
    and `graphql(&self, query: &str, vars: Value)`.
  - It uses an RS256 App JWT and `POST /app/installations/{id}/access_tokens`, caching the token for 50 min. The API
    base is overridable only with `REINS_TEST_ALLOW_LOOPBACK`.
  - Setting it up is `AdminAction::SetGithubReader { app_id, installation_id }` (two-person). The PEM is posted
    separately and sealed.
- **`codeowners.rs`:**
  - `pub struct Rules(Vec<(Pattern, Vec<Owner>)>)`, with `enum Owner { User(String), Team { org: String, slug: String
    }, Email(String) }`.
  - `pub fn parse(text: &str) -> (Rules, Vec<usize> /* skipped lines */)`. It follows GitHub's syntax:
    - `#` comments, `\#` escapes;
    - `*`, `**` and `?`; a leading `/` anchors; a trailing `/` means a directory;
    - `!` and `[ ]` aren't supported by GitHub, so those lines are skipped and reported;
    - a pattern with no owners clears ownership.
  - `pub fn owners_of(rules: &Rules, path: &str) -> Vec<Owner>`: the last match wins.
  - `pub async fn owners(conn, org, repo: &str, paths: Option<&[String]>) -> Resolution`:
    - it reads the **default branch's** `.github/CODEOWNERS`, then `CODEOWNERS`, then `docs/CODEOWNERS`, with a 5 min
      cache by blob SHA;
    - teams expand with `/orgs/{org}/teams/{slug}/members` (cap 500);
    - a login counts only when `reins_org_people.github_login` is verified;
    - `None` paths, or more than 3000, take the owners of the `*` rule, plus `unresolved: ["paths unknown"]`.
  - Paths come from:
    - `github_api_write` merging a PR (`PUT /repos/{o}/{r}/pulls/{n}/merge`): `GET /repos/{o}/{r}/pulls/{n}/files`;
    - a `git_lease` push, which has no paths (O2's lease is repo-wide), so the default owners apply.
  - GitHub login links are verified two ways:
    - `saml`: GraphQL `organization.samlIdentityProvider.externalIdentities`, whose `nameId` equals the member's email,
      re-checked daily;
    - `oauth`: the member authorizes the reader App from the console's "Link GitHub"; only the login is kept.

## What changed while building

Reconciled with O2 as merged (#242):
- `decisions::submit` is synchronous inside one transaction, so code owners and on-call (network calls) are asked
  first: `routing::prefetch` evaluates the request, asks the sources, and hands their answers to `submit_with` as
  `Dynamic` (keyed by repository and paths, or alias). The sweeper does the same per request before escalating.
- `reviews::notify(pool, users, subject)` has no org; the channel fan-out looks the request up by id.
- The agent's reason travels in the sealed request body and in `DecisionRecord.reason` (the executor judges a
  `require_reason` permit with it); `channel_allowed` takes the trace's level text (`"L0"`…), since `reins-proto`
  has no `Level`.

Deviations:
- **Eligibility.** A resolution is an *additional* eligible set per obligation (escalations add people to it), never
  the requester. Executors keep only members the obligation's reviewers or chain admit by the roster; the roster gains
  `backups` (group → backup group) so `BackupOf` is checked rather than trusted.
- **Resource owners** come from a new signed `OrgPolicy.resource_tags` (tag → resource glob → owner), since O2's facts
  have no tags.
- **Amounts** use `TemplateParams.currency` / `OrgRule.currency` as an ISO code (no `Currency` type exists); a purchase's
  amount is the payments Cart parser's `total`, and disagreeing amount fields fail closed. **New payees** are
  merchants whose site has no domain or host fact.
- **Connector reads** carry no resource in P2's context graph, so the Customer data template's reason-permit covers
  leases and repository-named effects, not `github_api_read` paths.
- **GitHub reader:** the table, model and client are O4's (`2026-11-01-000000_reins_org_github_reader`, identical
  files); O3 adds no reader columns. A key in place is replaced only by setting the reader to another app.
- **Slack install** takes the org's own app's bot token and signing secret (no OAuth dance), like Teams.
- **Web passkeys** use attestation `none`: device binding is as the browser reports (documented). The phone confirms a
  passkey by its key hash and registration time; a refusal is an unsigned revoke.
- **Channels** are bound to their install: a reinstall with another app or secret turns a channel off and lapses
  pending enables; a Teams bot id is one org's (proved with a client-credentials token, unique in the database).
- **Teams activities** need a key endorsed for the channel and a `serviceUrl` claim equal to the activity's, on exact
  Microsoft connector hosts.
- **Not built:** the console's "Link GitHub" OAuth for logins (SAML links, re-checked daily, are built); the pilot's
  week and its median are still to be recorded in 07 §1.
- **e2e:** one test, `org_routing::org_routing_end_to_end`, covers the four scenarios in order on one pilot org.
