# Decisions v2 · P4: deferred decisions and tickets. Implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a request that nobody answers within its Instant window, that the agent asks to defer, or that the reviewer
moves with **Decide later**, becomes a durable **ticket**. The agent carries on and collects the outcome later through
MCP, a webhook, the desktop inbox or a parked git push. The reviewer finds it under **Waiting for you**.

**Architecture:**
- The relay keeps Instant requests in memory exactly as today.
- A ticket is a row in `reins_tickets`. It holds metadata only in clear (ticket, state, deadlines, connection, request
  digest), plus the body **sealed on the server** to the approval device's X25519 box key. The server then drops its
  clear copy.
- Every transition is an event in `reins_ticket_events`:
  - transitions the phone makes are signed with its device signing key (Ed25519);
  - transitions the server makes (deferral on timeout, cancellation, expiry notice) are recorded unsigned and marked as
    the server's.
- Who executes and when (08 R9):
  - Writes execute on the phone when approved; the server keeps a minimal result.
  - Reads and desktop answers (credentials, `reins ask` passes) execute when collected; the server keeps nothing.
- Webhooks deliver only phone-signed events.

**Tech stack:**
- Rust 1.98.1: `reins-proto`, the server (`src/`, Rocket, Diesel), `reins-core` (UniFFI) and `reins-desktop`.
- Kotlin/Compose and Swift/SwiftUI.
- `crypto_box` 0.9 (sealed boxes, already in the lockfile) for the server's seal; `ring` for Ed25519 verification on the
  server (already used).

**Spec:**

## Global Constraints

- Personal mode stays end-to-end. The server never stores request bodies, read results or the agent's replies in clear
  beyond transit. A stored body is sealed to the approval device. A stored result is the minimal result of a write
  (08 R9).
- Windows:
  - Instant: default **120 s**, max **600 s**;
  - Deferred: default **4 h** (14 400 s), max **7 days** (604 800 s).
  - Server settings `REINS_INSTANT_WINDOW_SECS` and `REINS_DEFERRED_WINDOW_SECS`, clamped to those bounds.
- At most **50** open tickets per connection. Duplicate requests (same digest, same connection, still open) share a
  ticket.
- An approval stays valid for **1 h** for agent-run commands and **24 h** for executor-run actions (03 §6).
- **Auto never denies.** P4 adds no automatic denial: an expired ticket is "not approved", reported as Expired.
- Notifications only for things the user must act on: the deferred arrival, and reminders at **50%** and **90%** of the
  window.
- Batch approve never includes a request that isn't marked routine (`quick`). That is P4's stand-in for "never across
  L3" until P1/P2 deliver levels. Batch deny may include anything.
- Ownership:
  - P0/P1 own `crates/reins-policy` guard, shell and effect code; P4 doesn't touch them.
  - P4 owns lifecycle, transport and storage.
- Builds and tests:
  - Rust: `-j 4`, narrow `-p`; tests with `XDG_CONFIG_HOME` under `~/Documents/dev/tmp/dv2-p4/`; never `/tmp`;
  - clippy with the pinned 1.98.1 toolchain (`target-198`); `cargo fmt`;
  - Android: `cd android && env -u ANDROID_SDK_ROOT ANDROID_HOME=$HOME/Android/Sdk ./gradlew --max-workers=4 :app:testFullDebugUnitTest`;
  - iOS: `scripts/ios-typecheck.sh`.
- Copy is short; icons are real (Material Symbols, SF Symbols), never emoji. Commits and PRs never mention AI.

## Review Focus

1. **A server that lies about a ticket.** It might claim `approved`, swap the body, or replay an old approval.
   - The phone executes or collects only what its own local approval record covers, with the digest re-derived from
     the opened body.
   - Webhook consumers verify the device key.
   - Tests: `collect_without_local_approval_is_refused` (core), `digest_mismatch_body_is_rejected` (core).
2. **Another connection's ticket id.** Every server lookup filters by the caller's connection. A guessed id answers as
   unknown. Test: `tickets_are_scoped_to_their_connection` (server).
3. **The world moved between approve and execute** (remote branch moved, approval older than its validity). The
   result is Stale or Expired, never an execution. Tests: `moved_remote_is_stale_not_pushed` (desktop),
   `approval_past_validity_is_not_collected` (core).
4. **A phone that never published a box key** (an older app). Requests behave exactly as today: no deferral, expiry
   at 10 min. Test: `without_a_box_key_nothing_is_deferred` (server).
5. **An agent flooding tickets or polling hard.** Covered by the 50-ticket cap, the existing per-connection rate limit
   (`reins_wait` counts as a call), and at most 2 event streams per connection. Test:
   `the_fifty_first_open_ticket_is_refused` (server).

The state machine follows 03 §2, plus `needs_info`. A ticket can be decided straight from the inbox, without a
separate *opened* event.

| From | To |
|---|---|
| `Received` | `Reviewing`, `Deferred`, `Approved`, `Denied`, `Cancelled` |
| `Reviewing` | `Approved`, `Denied`, `Deferred`, `NeedsInfo`, `Cancelled` |
| `Deferred` | `Reviewing`, `Approved`, `Denied`, `NeedsInfo`, `Expired`, `Escalated`, `Cancelled` |
| `NeedsInfo` | `Deferred` (the agent replied), `Approved`, `Denied`, `Expired`, `Cancelled` |
| `Escalated` | `Reviewing`, `Approved`, `Denied`, `Expired`, `Cancelled` |
| `Approved` | `Revalidating`, `Executing`, `Done`, `Failed`, `Stale`, `Expired` (the approval's validity ran out uncollected) |
| `Revalidating` | `Executing`, `Stale` |
| `Executing` | `Done`, `Failed`, `Unknown` |
| `Stale` | `Reviewing`, `Approved`, `Denied`, `Expired`, `Cancelled` |

- Terminal states: `Done`, `Denied`, `Expired`, `Cancelled`, `Failed`, `Unknown`.
- Open states: `Received`, `Reviewing`, `Deferred`, `NeedsInfo`, `Escalated`, `Stale`.
- `webhook_type`: `Approved`→`ticket.approved`, `Denied`→`ticket.denied`, `Expired`→`ticket.expired`,
  `Stale`→`ticket.stale`, `Done`→`ticket.done`; anything else → `None`.

`execution(call)`:
- `OnCollect` for:
  - `GmailSearch`, `GmailRead`, `ListAccounts`, `RequestUpload`;
  - a `Connector` whose spec effect isn't `Write`;
  - any desktop-only connector tool.
- `OnApprove` otherwise: `GmailSend`, `RequestGrant`, connector writes, `Mcp`. MCP read hints come from a third
  party, so they're treated as writes.

`minimal_result` keeps:
- `Sent` → `{id, thread_id}`;
- `Granted` → `{granted, expires_at, max_uses}`;
- `Connector{data}` → only the top-level scalar keys among `id, node_id, number, sha, html_url, url, status, state,
  created_at, updated_at, message_id, event_id, ok`;
- `Mcp{result}` → `{isError}`;
- anything else → `{}`.

Rules:
- `park`:
  - refuses `NoBoxKey` when the approval device published no `box_pub`;
  - refuses `TooMany` at 50 open tickets for the connection;
  - with an open ticket of the same digest, returns it.
  - Otherwise it inserts with:
    - state `deferred`;
    - `deadline = now + clamp_window(Deferred, window)`;
    - `sealed_body = seal_body(box_pub, SealedTicketBody{request})`;
    - `execution`;
    - an unsigned event `{state: "deferred", by: "server"}`.
  - It then drops the relay entry, which wakes waiting calls with `WaitResult::Deferred(ticket)`, and pushes the phone
    (`PushKind::Req` with the request id).
- `apply_signed`:
  - verifies each event with `ring` Ed25519 against the device's `sign_pub`;
  - checks `event.ticket == ticket_of(id)`, `event.digest == ticket.digest` and `event.connection_id` match, and that
    `can_go` allows the move;
  - stores the event, updates the row (`note`, `result` as given, `stale`, `deadline` for `Deferred`), notifies the
    watch, and fires webhooks (Task 6).
- The sweeper:
  - converts relay entries past `instant_until` (unanswered) with `park`; failures leave the entry to expire as today;
  - moves due Deferred, NeedsInfo or Escalated rows to Expired, or to Escalated once when `on_expiry = escalate` and
    not yet escalated (the deadline restarts with `window_secs`), and pushes the phone;
  - moves `Approved` rows past their approval validity to `Expired` (`approved_at` is the latest `approved` event:
    1 h for `desktop_ask`, 24 h otherwise).

  - `GET /mcp` without that `Accept` stays 405.

Rendering:
- A deferral returns the non-error object from 03 §4.1, as `structuredContent` plus text:
  `{status:"pending_review", ticket, summary, expected_by, next}`.
  - `summary` is built from the clear call at that moment and never stored:
    `"<tool title>: <first argument line> — waiting for your approval"`, ≤ 120 chars.
  - `next` is:
    `"Continue with other work. Call reins_get_result with this ticket later, or reins_wait to block up to 10 minutes."`
- Statuses as `reins_get_result` returns them:
  - `deferred` → `pending_review` (no summary);
  - `needs_info` → `{status:"needs_info", ticket, question, next:"Answer with reins_reply(ticket, text)."}`;
  - `approved`:
    - `OnCollect` → a collect: the phone runs it now, and the result passes through;
    - `OnApprove` → waits for `done`;
  - `done` → the stored minimal result, plus `note:"Approved and done. The full result was not kept."`;
  - `denied` → an error result: `Denied on the user's Reins device.` plus `Reviewer's note: "<note>"` when there is
    one;
  - `expired` → an error result: `Expired: not approved in time.`;
  - `cancelled`, `stale` → an error result with the stale diff.
- `render_outcome` for an Instant `Denied{reason: Some(r)}` appends `Reviewer's note: "<r>"`. The reason was dropped
  before.
- The instructions gain one line:
  `If a result says pending_review, continue with other work and check the ticket later with reins_get_result or reins_wait.`

Rules:
- Sync:
  - Opens each `TicketItem` with `box_key()`. It checks that the opened request's id equals the item id and that
    `request_digest(...)` equals `item.digest`; otherwise it drops the item and logs.
  - It parks the item with `ticket` metadata. The pending TTL for it is its `deadline`, not 600 s.
  - Items in a terminal state, or `expired`, are removed. For `expired`, the phone signs and posts an `Expired` event
    once.
- Approving a ticket revalidates first:
  - the digest is re-derived from the stored request;
  - the connection still exists;
  - the ticket isn't past its deadline.
  - Then:
    - `OnApprove`: execute as today, and respond with events `[Approved, Done{minimal}]`, or `[Approved, Failed]`.
    - `OnCollect`: store `ticket_approvals(id, digest, approved_at, valid_until)` and post `[Approved]`.
- Collect (`item.collect`):
  - Requires a local approval with the same digest and `valid_until > now`. It then runs the request through the normal
    execution path, skipping the user, and responds with the result.
  - Otherwise it posts `Expired`, past validity, or `Stale`, digest differs.
- `desktop_ask` answers include `digest` (the topic digest the desktop sent in `arguments.digest`) and
  `expires_at = approved_at + 3600`.
- `decide_later` signs a `Deferred` event (`window_secs` = default) for an Instant request, posts it, and keeps the
  card with the new deadline.
- `ask_why` posts `NeedsInfo` with the question (≤ 500 chars).
- `deny_with_note` responds with `Denied{reason: note}`, plus a `Denied` event with `note` for tickets.

Rules:
- The hook's `PreToolUse` checks `take_pass(command_digest)` first and allows with the reason
  `Approved earlier (ticket rt_…)`. On a deferred answer it records the ticket and denies with:
  `Parked for review (ticket rt_…, expected within 4 h). Continue with other work; when it's approved, re-run this exact command.`
- On any hook event of a session, the hook injects `news_for(session_id)`:
  - Claude Code `PreToolUse` and `UserPromptSubmit`: `additionalContext`;
  - Claude Code `Stop`: `{"decision":"block","reason": news}`, only when news exists.
  - The texts:
    - `Reins: rt_… (<summary>) was approved — re-run it now.`
    - `… was denied: <note>`
    - `… expired, not approved.`
    - `… is stale: <diff>.`

  collects approved `Hook`/`Ask` tickets (sealed `AskAnswer` → `grant_pass`) and approved `Push` tickets (the sealed
  `CredentialGrant` for the stored digest).

  - When the phone defers a push, the proxy keeps the spooled request body in `state_dir/parked/<ticket>.body` (at
    most 256 MiB, else it isn't parked and the push fails as today), with its upstream URL, commands and digest.

    `Reins: parked for review (ticket rt_…). It will be pushed when approved; you can keep working.`
    git exits non-zero.
  - On approval:
    - `info/refs?service=git-receive-pack` with the credential; each command's `old` must equal the advertised tip
      (force-with-lease);
    - else `POST …/tickets/<t>/stale` with `"<ref> moved from <old7> to <now7>"`, and the push isn't sent.
    - Pushes to the same `(repo, ref)` go in ticket order; a later one waits while an earlier one is open.
- `reins tickets` prints a table of local tickets with live state. `reins wait <ticket> [--timeout secs]` exits 0 on
  approved (done), 1 on denied, 2 on expired, stale, cancelled or timeout.
