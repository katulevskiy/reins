# Reins for iOS and iPadOS

A native SwiftUI app around the same Rust core as the Android app (`crates/reins-core`), which owns all logic,
networking, grant evaluation and encrypted storage. Swift does the interface, the keychain, Face ID, APNs and
notifications, widgets, Live Activities, Google sign-in, the phone's calendar and contacts, and ONNX Runtime for
Autopilot. It runs on iPhone, iPad and the foldable iPhone Duo (iOS 26 or later).

## Build

Needs Xcode 27.1 for the iPhone Duo's fold (`UIHinge`, and its simulator runtime), or Xcode 27.0, which builds the app
without it (the fold reads as flat; `REINS_HINGE_CONDITION` in `Config/Reins.xcconfig`). App Store and TestFlight uploads
need a released Xcode, so they use 27.0 while 27.1 is in beta. Also Rust (`rustup`; the targets `aarch64-apple-ios` and
`aarch64-apple-ios-sim` are added by the build script). Apple silicon only.

```bash
export DEVELOPER_DIR=/Applications/Xcode-27.1-beta.app/Contents/Developer
ios/scripts/build-core.sh iphonesimulator            # once, ~5 min: the core as a static library + Swift bindings
open ios/Reins.xcodeproj                              # or:
ios/scripts/sim.sh "iPhone 18 Pro Max" --shot /tmp/reins.png -- -demo
```

The app target's "Rust core" build phase runs `build-core.sh` for the active platform (Debug: `release-low`, Release:
`release`, thin LTO; uniffi-bindgen itself is built with the cheap `host-tool` profile). `REINS_SKIP_CORE=1` reuses the
last build while iterating on Swift. The generated bindings
(`ios/Core/Generated/reins_core.swift`) are committed, so Xcode's synchronized folders always see them.

`ios/Reins.xcodeproj` is generated by `ios/scripts/gen-project.py` (targets, folders, build settings, the ONNX Runtime
package). Folders are synchronized groups: new files need no project change. Change targets or settings in the script
and re-run it; do not edit the project file by hand.

### Compile check on Linux

```bash
scripts/ios-typecheck.sh                      # all targets, Debug: ~10 s warm
scripts/ios-typecheck.sh Reins ReinsTests     # some (also: app widgets notifications tests uitests)
scripts/ios-typecheck.sh --release            # Release's conditions (no DEBUG); --warnings shows warnings
```

It type-checks each target's Swift with `swiftc` against the iPhoneOS 27 SDK (`arm64-apple-ios26.0`), with the
target's folders, compilation conditions (`REINS_APP`, `DEBUG`, `REINS_HINGE` per SDK, ...), Swift version and
extension-only API rules, all read from `gen-project.py` and `Config/Reins.xcconfig`. The app emits its module so
`ReinsTests` checks its `@testable import Reins`. SwiftUI's macros (`#Preview`) expand through the SDK bundle's macro
server. It prints one line per target and exits non-zero with the compiler's errors.

Needs Swift 6.4 ([swiftly](https://www.swift.org/install/linux/)) and the Darwin Swift SDK that
[xtool](https://github.com/xtool-org/xtool) makes from an Xcode .xip (`xtool setup`; it lands in
`~/.config/swiftpm/swift-sdks/darwin.artifactbundle`, or set `REINS_DARWIN_SDK`). The first run (about 1.5 min) also
builds the Rust core for the host, to generate `reins_coreFFI.h` with uniffi-bindgen as `build-core.sh` does, and
fetches ONNX Runtime's headers at the version `Package.resolved` pins (checksum checked). Both are cached in
`~/.cache/reins-ios-typecheck` (or `$REINS_IOS_TYPECHECK_CACHE`). The core build is keyed by a content hash of the
core's sources, the crates it depends on, Cargo.lock, the UniFFI config and the toolchain, one directory per hash,
and the last three builds are kept, so worktrees that share the cache each use the build for their own sources.
Nothing is stubbed. Asset symbols (`ImageResource.foo`) are generated from the asset
catalogs as Xcode does.

It does not link, sign or run anything: no simulator, no unit or UI tests run, no asset catalog, storyboard or
Info.plist processing, no entitlements. A missing symbol in the Rust static library, a resource name that does not
exist, or a crash only show up in an Xcode build. CI cannot run it: the SDK comes from Xcode, which is licensed for
Apple hardware, so there is no CI job.

### Configuration

`ios/Config/Reins.xcconfig` holds the shared settings; machine-specific ones go in `ios/Config/Local.xcconfig`
(git-ignored, see `Local.xcconfig.example`):

| Setting | What it is for |
|---|---|
| `REINS_TEAM` | Your Apple developer team, for device builds (simulator builds need none) |
| `REINS_TELEGRAM_API_ID`, `REINS_TELEGRAM_API_HASH` | Telegram (your own account); without them Telegram is unavailable |
| `REINS_GOOGLE_CLIENT_ID`, `REINS_GOOGLE_REDIRECT_SCHEME` | An iOS OAuth client of your Google Cloud project and its reversed id; without them Gmail, Google Calendar and Contacts say "needs setup" |
| `REINS_APS_ENVIRONMENT` | `development` for Debug, `production` for Release (also picks the push-token prefix the server sees) |

Push notifications need APNs on the server: `REINS_APNS_KEY_FILE`, `_KEY_ID`, `_TEAM_ID`, `_TOPIC` (see
[docs/self-hosting.md](../docs/self-hosting.md)). Without them requests still arrive while the app is open (long poll).

### TestFlight

Every release goes to TestFlight by itself: once the release is published, the release workflow's `ios-testflight` job
archives with Xcode 27.0 on GitHub's `xcode-27` runner, signs manually with the Apple Distribution certificate and the
App Store profiles of the three targets, and uploads it, and `scripts/testflight.py` sets export compliance, What to Test (the release notes), the
groups ("Internal", and the external "Testers" by its id) and the beta review submission. Version: the release's; build
number: the Android versionCode, kept above any build already in App Store Connect. No Mac is needed per release.
Secrets, variables and the one-time setup: [CONTRIBUTING.md](../CONTRIBUTING.md#maintainers-testflight).

## Sign-in and recovery

Hosted sign-in uses WorkOS AuthKit in an authentication browser session, with a passkey instead of a Reins master
password. Passkeys and a stable AuthKit custom domain must be configured in the WorkOS environment. Self-hosted
servers retain their own SSO and password compatibility under “Use another server”.

Passwordless accounts must write down their recovery code before the normal app screens appear. The user confirms
that it is stored safely and types the final group from the written copy; copying the code does not complete the
step. The gate resumes after an app restart. Only a fingerprint acknowledgement is saved outside the encrypted core,
so WorkOS email changes do not repeat the step and a replaced recovery code does. The authenticated account id is
cached by the core, allowing recovery-code access offline after subsequent restarts; an older installation may need
one online token refresh. Settings shows the recovery code again after Face ID, Touch ID or the passcode.
Settings > Session > Delete account explains what is deleted, asks for the account's email and calls the core's
`deleteAccount`, which deletes the account on the server (with its WorkOS user) and the phone's encrypted copy; the
app then forgets the account as signing out does. With `-demo` it only signs out.

## iPhone, iPad, iPhone Duo

The same navigation state drives two shells: a Liquid Glass tab bar (Activity, Grants, Autopilot, Settings) on a
compact width, and a three-column split view on a regular one (iPad, Stage Manager windows). Resizing, rotating or
unfolding keeps what is open. On the iPhone Duo, `UIHingeInteraction` (iOS 27.1) reports the fold to SwiftUI
(`@Environment(\.hinge)`); a bent device keeps decision buttons out of the crease in large sheets.

## Notifications, widgets, Live Activities

- Requests arrive as time-sensitive notifications with the Reins chime (`reins_request.caf`); the extension rewrites
  the server's content-free push into "Approval needed · Claude: Send email to 2". Deny works from the notification
  (unlocked phone); approving always opens the app and asks for Face ID. Autopilot's decisions are quiet notifications
  with "Report". Grants ending soon remind you. Sounds follow Settings > Sounds & haptics.
- With the app in front a request posts no notification (it pops up instead), but it still chimes once, with a haptic
  ("Sound when open", on by default): only for a request that waits for you, once per request, at most once every 3 s
  (`ArrivalPolicy`), in the `.ambient` session, so the ring/silent switch mutes it and music keeps playing.
- Only what waits for you is an ask. A bypass, Lockdown, Overnight, Auto and standing grants decide first; the core's
  `pending` lists only what they leave to you, and what they decide shows in Activity, never as an ask, a card or an
  actionable notification. An ask on screen that a mode decides meanwhile closes by itself, and its notification goes.
- When Autopilot needs its model (Manual, Auto, Overnight), the extension parks the request without judging it
  (`handle_push_deferring_autopilot`) and the app judges it when it next runs; the push also wakes the app. In the
  background the app does the same unless the model is already loaded (`set_background`): it is judged in front.
  Meanwhile an Auto or Overnight request is not yours yet (`deciding`): its notification says "Open Reins so Autopilot
  can decide", with no action. A push the extension cannot read in time shows the generic text without Deny.
- Background time: the store's file lock in the App Group container is only ever held under a background task (the
  app) or an expiring activity (the extension), through `SuspensionGuard` (`install_store_lock_guard`); iOS ends a
  process suspended with it held (`0xdead10cc`). A lock the other process keeps fails the call as busy after a few
  seconds instead of waiting. A background push or refresh completes within `BackgroundBudget.limit` (20 s) whatever
  is still running, and reads only what waits; the rest is read when the app comes to the front.
- Widgets: what waits (with countdowns), Autopilot (Lock down, Stop bypass), latest activity; Lock Screen gauges.
- Live Activities: requests waiting (Deny / Review in the Dynamic Island), a running bypass (Stop), the model download.
- Controls and Siri: "Lock down Reins", "Stop the Reins bypass", "Show what is waiting in Reins".

in the real app and pairs a simulated computer by its code (`reins login`'s device flow).

## Pairing a computer

`reins login` and the desktop app show a QR code for `https://<server>/pair?code=BCDF-GHJK` and the code under it.
The phone scans it in the app (VisionKit; Settings > AI connections > Connect a computer, or the onboarding step),
opens it as a universal link (Associated Domains `applinks:app.reins2fa.com`; the server serves the
`apple-app-site-association` file when `REINS_APPLE_TEAM_ID` is set), as `reins://pair?code=...`, or takes it
typed. Only the code is used, redeemed on the phone's own server (`pairingByCode`); the pairing sheet then asks for the
number the computer shows and compares its key. Without a camera (the simulator) the code is typed.

## Not on iOS

- Text messages: iOS gives apps no access to SMS, so that integration is listed as unavailable.
- The in-app updater of the Android `full` build: iOS apps update through the App Store or TestFlight.
- Haptics and the Dynamic Island need a real iPhone to be felt and seen in full; the simulator has neither a Taptic
  Engine nor working APNs pushes.
